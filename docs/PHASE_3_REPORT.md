## 2. 指標：與 TA-Lib 精確吻合

`QUANT_ENGINE.md` §1.1 早就寫明「不依賴 TA-Lib 作為執行期依賴，但用它當測試黃金基準」。
把容忍度定在 `rtol=1e-6` 之後，這句話長出了牙齒。

**天真的實作會過 `1e-2`，而且永遠過不了 `1e-6`。** 所有遞迴平均（EMA、Wilder、ATR、
ADX、MACD）從第一筆開始遞迴的版本，與 TA-Lib 的誤差約 1%，隨序列拉長而收斂 ——
畫成圖分不出來，但每一個回測都會被推移一點點。

實測逼出來的三件事：

| 發現 | 影響 |
|------|------|
| **+DI／−DI 的累加種子是 `window - 1` 筆，不是 `window` 筆** | DI 是兩個這種和的比值，差異不會相消。第一個輸出差 0.3 |
| **MACD 的快線 EMA 在慢線的起點播種**，用的是結束於第 25 根的 12 根 K | 「自然」的播種法會讓 MACD 線在前一百根差約 0.2 |
| **MACD 線只能從 signal 存在處開始發布** | 否則同一條線的值會隨 signal 週期而變 —— 同一個序列悄悄變成不同意思 |

三個**刻意不吻合**的，各自有測試說明理由（不是放寬容忍度）：

- `kd_k` / `kd_d` 用台股慣例（RSV 逐次取三分之一），不是 TA-Lib 的 `STOCH`。
  兩者是同名的不同指標，台灣每一個看盤軟體都顯示前者
- `roc` 回傳分數而非百分比 —— 下游全部用分數，一個指標大一百倍是活得過 code review 的錯
- `beta` / `alpha` / `corr` / `idio_vol` TA-Lib 沒有，改與 numpy 最小平方法對照

另有一個測試**證明這個檢查會失敗**：把天真實作餵進去，斷言它在 `1e-2` 下通過、
在 `1e-6` 下失敗。§17 已經付過「不可能失敗的檢查」的學費。

決策記錄在 **ADR-026**。

## 3. Look-ahead 注入測試（★）

`QUANT_ENGINE.md` §10.2 稱它是整個系統最重要的一條測試。實作方式如規格：
把 cutoff 之後的每一欄乘以 1000，重算，斷言 cutoff 之前**沒有任何一個數字改變**。

**111 個測試**，對每一個指標、每一個可計算因子的 `raw_value` 與 `score` 各跑一次
—— 不是挑幾個代表。這條性質的價值在於它普遍成立；只驗證想得到的那幾個，
正是漏洞活下來的方式。

另外三條：

- **這個方法本身會失敗**：注入一個 `close.shift(-1)` 的假指標，斷言測試抓得到
- **forward return 不會跨越股票邊界**：整張表 `shift(-20)` 會讓一檔股票的最後 20 列
  拿到下一檔的前 20 列。不會報錯，只會讓 IC 變好看
- **每檔股票的最後 20 個 session 的 forward return 必須是 null**，不能是借來的

## 4. 因子：53 個宣告，16 個可算

宣告不可算的因子不是樂觀，是**對資料管線的陳述**。

| 類別 | 宣告 | 可算 | 等什麼 |
|------|------|------|--------|
| momentum | 6 | 6 | — |
| volatility | 5 | 5 | — |
| liquidity | 4 | 4 | — |
| size | 2 | 1 | `free_float_shares` |
| value | 6 | 0 | `eps_ttm`、`book_value_per_share`… |
| growth | 7 | 0 | `revenue_yoy`、`eps_yoy`… |
| quality | 11 | 0 | `roe_ttm`、`accruals`… |
| sentiment / news | 7 | 0 | Phase 4 |
| ai_exposure | 5 | 0 | Phase 5 / 7 |

Value / Growth / Quality 全部缺 —— 它們等的是 Phase 2 roadmap 裡列出但**尚未實作**的
月營收與財報 ingestion。這一格空著，比因子清單裡沒有它們更有用。

處理管線固定順序：`winsorize → 產業中性化 → 市值中性化 → 標準化 → 方向`。
每一步都是**橫斷面**的（同一天跨股票），這使整條管線在結構上不可能 look-ahead ——
`t` 日的值只是 `t` 日各值的函數。

`direction` 最後才套用，所以 `raw_value` 存的是一般引用的量（`hv_60` 是波動率，
不是負波動率），可以拿去對外部來源核對；`score` 才是「越大越好」。

## 5. 因子有效性：真實資料上的結果

實測 2026-02-02 → 2026-08-14，20 日前瞻報酬：

```
factor                    verdict            IC    RankIC     IC-IR  dates
momentum_consistency_60   RESEARCH_ONLY  -0.1703  -0.1493   -0.8097     68
log_market_cap            RESEARCH_ONLY   0.0679   0.0309    0.3811    107
avg_turnover_20d          RESEARCH_ONLY  -0.0537  -0.0289   -0.5708    107
hv_60                     RESEARCH_ONLY   0.0497   0.0261    0.6102     68
momentum_1m               RESEARCH_ONLY  -0.0319  -0.0371   -0.1025    107
turnover_rate_20d         RESEARCH_ONLY   0.0142   0.0045    0.0551    107
downside_deviation_60     RESEARCH_ONLY   0.0037  -0.0339    0.0461     68
（9 個 INSUFFICIENT_DATA，37 個 NOT_COMPUTABLE）
```

**0 個通過。** 主要原因不是因子沒訊號，而是**覆蓋率 2.5%** ——
全市場 1,378 檔，只有 38 檔有歷史（見 §6）。門檻要求 70%。

有兩件事值得注意，因為它們證明檢查在運作：

1. **`hv_60` 與 `downside_deviation_60` 相關 0.96** —— 冗餘檢查在真實資料上抓到了。
   兩者測的是同一件事，規格說 >0.8 要擇一保留
2. **`momentum_consistency_60` 的 IC 是 -0.17、IC-IR -0.81**，看起來很強。
   在 38 檔股票、68 個日期上，這是雜訊。覆蓋率門檻擋下了它 ——
   **這正是門檻存在的理由**：一個看起來很強的因子是最危險的那種

## 6. 為什麼只有 38 檔有歷史

跑實際回補時撞到兩個真實限制，都不是程式問題：

**其一：全市場歷史端點不存在。**
TWSE 的 `STOCK_DAY_ALL` 是快照，沒有日期參數；歷史只能走 RWD 的
`STOCK_DAY`（單股單月）。十年全市場約 12 萬次請求 —— Phase 2 報告早就標記要避開。
這次抓的是成交值前 40 檔 × 8 個月 ≈ 320 次請求。

**其二：交易日曆只有 2026 年。**
第一次回補抓 2024–2026 共 24 個月，結果 **2,194 列進了隔離區**，規則 `CAL00`：
「該交易日沒有日曆記錄」。日曆的來源端點只服務當年度。

守門是對的 —— 沒有日曆就不知道那天市場是否開市，猜測會把颱風假寫成交易日。
但它也意味著**歷史回補必須先有歷史日曆**，而目前沒有來源。
可行做法是用「當日全市場成交量 > 0」反推歷史交易日（`verified_by_volume` 欄位已存在），
這是 L1 的一部分，尚未實作。

## 8. 這一階段抓到的缺陷

| # | 缺陷 | 怎麼被抓到 |
|---|------|-----------|
| 1 | **指標在歷史不足時回傳長度不等於輸入長度** | 對真實的單日全市場資料執行時 polars 直接拋錯。新上市股票就是這個情況 —— 補零的 warm-up 比輸入還長 |
| 2 | **KD 在視窗未滿時回傳 50 而非 null** | §1.3 明寫「上市未滿 window 日 → null，不用較短視窗代替」。50 是一個捏造的中性讀數 |
| 3 | **numpy 2.5 需要 Python 3.12，執行期映像是 3.11** | 本機解析到 2.5、容器會解析到 2.2 —— 兩個不同的函式庫，只型別檢查過一個。已加上上界並註明理由 |
| 4 | **`_pearson` 用 `corrcoef` 會被單一 NaN 汙染** | 相關矩陣在真實資料上噴 RuntimeWarning。改成成對刪除（pairwise deletion） |
| 5 | **`evaluate` 量測成功後仍留在 `INSUFFICIENT_DATA`** | `apply_thresholds` 對該狀態直接返回，於是每個量測過的因子都看起來沒量測過 |

第 1 與第 2 項只有**真實資料**會暴露 —— 合成的測試面板每檔都有 400 根 K 線。
這與 Phase 2 §13 第 8 項是同一個教訓的不同版本。

## 9. 效能實測

| 作業 | 規模 | 實測 | 預算 |
|------|------|------|------|
| 單日全市場指標 + 因子 | 1,378 檔 × 76 指標 × 16 因子 | **25.1 s** | 180 s |
| ├ 載入 | 1,378 檔 × 最多 499 個 session | 1.1 s | |
| ├ 指標 | | 19.1 s | 60 s |
| ├ 因子 | | 4.4 s | 120 s |
| └ 寫入 | 1,378 + 2,757 列 | 0.5 s | |
| 歷史回算 | 148 個交易日 × 1,378 檔 | 約 90 s | — |

指標的 19 秒幾乎全是**逐檔的 Python 迴圈開銷**（1,378 次 × 76 個指標），

如果超出預算，向量化的方向是把同類指標改成一次 `group_by` 而非逐檔呼叫。

## 10. API 與前端

| 端點 | 用途 |
|------|------|
| `GET /quant/indicators/catalogue` | 這個 build 能算的每個指標（讀登錄表，不是讀資料庫） |
| `GET /quant/factors/catalogue` | 每個因子的完整規格 + 最新判定 + 缺什麼輸入 |
| `GET /stocks/{symbol}/indicators` | 某檔某日全部指標，含 `price_basis` |
| `GET /stocks/{symbol}/factors` | 因子雷達的資料 |
| `GET /factors/ranking` | 依 `score` 排序（方向已套用，所以 top 是「最好」不是「最大」） |
| `POST /screener` | 複合條件，**回傳通過的實際數值** |

前端兩頁：

- **`/screener`** —— 動態條件建構器、視窗化結果表、點列展開因子雷達。
  結果表顯示通過條件的實際值，因為任何人看到一份選股結果的第一個問題是「為什麼是它」
- **`/factors`** —— 因子目錄：判定、IC、IC-IR、完整規格、缺的輸入。
  **這一頁空的那一半才是重點** —— 它是「還沒接財報」與「沒有價值因子」的差別

選股器對沒有分數的因子回傳 **422 並指名該因子**，不是空結果。
「沒有股票通過」與「這個因子從沒算過」是不同的答案。

## 11. 架構決策

| ADR | 決策 | 為什麼會被問「為什麼要這樣」 |
|-----|------|------------------------------|
| **026** | 指標庫精確重現 TA-Lib 的 seeding | `core.py` 有一整段程式只為了模仿另一個函式庫的初始化。理由是 1e-2 會過、1e-6 不會 |

## 13. 停止點

Phase 3 的**工程**完成：引擎、測試、API、前端、排程、文件都在，而且全綠。

Phase 3 的**科學**沒有完成，而且不是靠寫更多程式能完成的 ——
它需要資料量。目前每一個因子的判定都是 `RESEARCH_ONLY` 或 `INSUFFICIENT_DATA`，
系統對此的陳述是準確的。

需要你的決定：

1. **L1 全市場歷史回補** —— 12 萬次請求（單股單月），或改用商業資料源。
   在此之前，Phase 5 的 AI Score 沒有可用的因子
2. **歷史交易日曆的來源** —— 用成交量反推是可行的，但要先有價格；先有雞先有蛋的解法是
   放寬回補時的日曆守門並在事後驗證，這需要你同意
3. **Phase 4（News）可以並行** —— 它不依賴價格歷史，且它的產出正好是 sentiment/news
   那 7 個因子缺的輸入
